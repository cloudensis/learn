# first-steps（仮題:AIと学ぶ、はじめてのソフトウェア開発）

この本の設計。章を書くときはここに従う。サイト全体の方針はリポジトリ直下の [README](../../../../../README.md) にある。

## 対象

ソフトウェア開発の知識がまったくない大学1年生をメインのペルソナとする。
高校生や、ソフトウェアの知識を仕事に活かしたい社会人も読めるが、書き方に迷ったらメインのペルソナで判断する。

サイトの入口にあたる一冊であり、**他のどの book / article も前提知識として要求しない**。ここだけは、本当に何も知らない読者から始める。

パソコンのファイルとフォルダの扱いは、読者によって理解の差が大きい。本文では扱わず article に切り出し、第1章で「不安な人はこちら」と案内する。

### 読者に用意してもらうもの

- Windows または Mac のパソコン1台（ソフトを入れられるもの）とインターネット接続
- メールアドレス
- AIとの対話ツールをひとつ。作ったページをその場で動かして見せる機能があるもの（ChatGPT・Gemini の Canvas、Claude の Artifacts など）。どれを使うかは読者が選び、本文は特定のサービスに依存した書き方をしない

それ以外は要求しない。**費用は0円、クレジットカードの登録も要らない**範囲に収める。

## この本のゴール

読み終えたとき、読者の手元に次の2つが残っている。

1. インターネットに公開された、自分で作ったゲームのURL
2. この本がなくても学び続けられる、AIとのやり取りの型

1 は動機を保つための成果物であり、2 がこの本の本題である。
題材は第2章で作るブラウザゲーム1本に絞り、最後まで同じゲームを育てる。

## やらないこと

最初の一冊で挫折させないため、次のものはこの本では扱わず、別の book / article に回す。

- **ターミナル（コマンド操作）** — 公開までを含め、画面の操作だけで進められる題材と公開先を選ぶ
- **Git / GitHub** — 成果物を作るうえで必須ではなく、入門で最も挫折が多い
- **サーバー側のプログラム** — 作るのは HTML・CSS・JavaScript のファイルだけにする

## 目標ごとの設計

サイト全体の3つの目標を、この本でどう扱うか。

### 目標1:次に何を学ぶかを、自分で決められる

- **学習活動** — 第3章で、ロードマップ専用のチャットを作らせる。以降、各章の終わりにそのチャットへ報告させ、現在地と次にやることを確かめさせる（→ ロードマップ用チャット）。
- **到達の確認** — 第10章。作りたいものを一つ決め、必要な知識と学ぶ順番を、理由つきでロードマップ用チャットに書き出せる。

### 目標2:分からないことをAIに聞き、返ってきた答えの正しさを自分で確かめられる

- **学習活動** — 第1章で「AIは間違える。確かめ方は、動かすことと公式資料の2つ」とだけ渡し、以降の全章に「確かめる」節を置いて、使いながら身につけさせる。独立した章は設けない。
- **到達の確認** — 第9章。この本が扱っていない機能について、AIの答えを動かして確かめ、公式資料とも突き合わせてから実装できる。

### 目標3:詰まったときに、原因の場所を切り分けてAIに相談できる

- **学習活動** — 第5章で、自分のゲームを**わざと壊させて**、エラー相談の型を初めて使わせる。自分で壊したものは必ず直せるので、最初の練習として安全である。英語のエラーは訳さず、全文をそのまま渡させる。
- **到達の確認** — 第8章。**本が用意した不具合**を切り分けて、テンプレートに沿った相談文を書ける。第7章の最後に、手元では動くが公開先でだけ壊れる変更を加えさせておき、原因は伝えない（例：ファイル名の大文字・小文字の食い違い）。

### 各部の意図

- **第1部**は、最短で「作れた」を体験させてから地図を渡す。第2章ではAIツールの中だけでゲームを作り、「自分のURLがない」「手元にファイルがない」「直し方が分からない」など、足りないものを読者自身に挙げさせる。第3章のロードマップは、その足りないものを埋める道のりとして作る。
- **第2部**は、第2章のゲームを手元に持ってきて、自分で触れるものにする。第5章で早めに壊しておくのは、第6章で必ずエラーに出会うからである。
- **第3部**でゲームが外に出る。Webの仕組み（ブラウザがファイルを受け取って表示する）は、独立した章にせず、公開の直前に必要なぶんだけ扱う。
- **第4部**がこの本の本題。第8章は本の手順に沿って切り分け、第9章は本の指示なしで作り、第10章は本の外に出ていく。**順に本の手を離していく**。題材は最後まで自分のゲームで、新しい題材を持ち込まない。

## 全編を貫く仕掛け

### 1. ロードマップ用チャット

学習の記録をファイルに残させることはしない。代わりに、AIツールの中に**ロードマップ専用のチャットを1つ**作らせ、それを最後まで使う。

- 第3章で作る。最初のメッセージで、自分の前提（知識がないこと）と、第2章で挙げた足りないものを渡し、ロードマップを作らせる。
- 使い道は**現在地の確認と、次にやることの整理だけ**に限る。質問やエラー相談は別の会話で行い、このチャットに持ち込まない。会話が長くなるほどAIの答えは散らかるため、コンテキストを汚さないことを第1章のコツとつなげて教える。
- 各章の終わりに、「この章で何ができるようになったか」を一言で報告し、現在地と次にやることを返してもらう。本文にはそのままコピーして送れる報告文を置く。
- チャットが長くなったら、それまでの要約を作らせて、新しいロードマップ用チャットに引き継がせる。
- 第10章の到達の確認は、このチャットの中で行う。

各章の冒頭では、本の目次のどこにいるかだけを示す。読者自身の現在地は、このチャットで確かめさせる。

### 2. 型の反復

サイト全体で使う5つの型を、この本では次のように配置する。初出の章で型そのものを教え、以降は説明せずに使わせる。1つの章で初出にする型は2つまでにする。

| 型                   | 初出 | 繰り返し使う章 |
| -------------------- | ---- | -------------- |
| 型2・部分を聞く      | 1章  | 全章           |
| 型1・全体像を聞く    | 3章  | 7章、10章       |
| 型3・理由を聞く      | 4章  | 6章、7章、10章  |
| エラー相談の型       | 5章  | 6章、8章       |
| 公式資料を参照させる | 7章  | 8章、9章       |

公式資料を参照させる型は、URLを開けないAIもあるため、**開けないときは本文を貼り付けて渡す**やり方もあわせて教える。

### 3. 詰まったときの共通ルール

第1章で渡し、各章の「つまずいたら」から毎回ここへ戻す。

- **AIの答えが本文の例と違う** — 違っていて当然である。答えが一致するかではなく、章の「次へ進んでよい状態」になっているかで判断する。
- **同じところで3回止まった** — 最後に動いた状態に戻し、新しい会話で、ここまでの状況を要約してから聞き直す。AIと堂々巡りを続けない。
- **それでも解決しない** — 「次へ進んでよい状態」の一歩手前まででよいとし、止まった場所をロードマップ用チャットに報告して日を改めさせる。人に聞ける窓口ができたら、ここに加える。
- **AIにも、公開する場所にも載せないもの** — パスワード、個人情報。第1章と第7章で扱う。

## 章の書き方

全章を同じ骨格で書く。編集方針6の「反復」は、型だけでなく**章の形そのもの**にも効かせる。

```
ゴール（1文）
手に入るもの
目安時間
いま目次のどこにいるか

やること
    何を達成したいか → プロンプト（コピーしてそのまま送れる形）
確かめる
    実際に動かして確かめる
    公式資料で確かめる（使える章だけ）
次へ進んでよい状態（ここまでできれば、残りは飛ばしてよい）
つまずいたら（共通ルールと、エラー相談の型へ）
ロードマップ用チャットに報告する
```

- 「確かめる」を**構造として必須**にしておけば、編集方針4は書き手の心がけではなくテンプレートによって守られる。
- 「次へ進んでよい状態」は、AIの特定の答えではなく**読者の手元の状態**で書く。AIの答えは読者ごとに違うため、答えを基準にすると判定できない。
- 「手に入るもの」は、動くゲームやURLのように**手元に実物が残るもの**に限る。メモや記録を成果物として課さない。
- 本の外（article や外部サイト）へのリンクは `target="_blank"` で新しいタブに開く。読者が本の中の現在地を見失わないようにするため。本の中の章や目次へのリンクは、同じタブで開く。
- 読者に何かを選ばせる場面（第2章のゲーム、第6章・第9章の機能、第10章の作りたいもの）では、**例をいくつかと決め方を添える**。白紙で選ばせると、そこで止まる。

## 技術の選択

作るのは HTML・CSS・JavaScript のファイルだけで、公開先は Cloudflare Workers とする。第7章では Cloudflare Drop を使い、ファイルの入ったフォルダをブラウザにドラッグ＆ドロップして公開する。

選んだ理由は次のとおり。

- **ターミナルも Git も要らない。** アカウントなしで試しに公開でき、そのあとアカウントを作って引き取れば、そのまま残る。
- **無料の範囲に回数の上限を気にせず収まり、クレジットカードも要らない。**
- **一次情報がAIに読ませられる形で整備されている**（`https://developers.cloudflare.com/workers/llms.txt`）。「公式資料を参照させる型」を教えるうえで、これが決定的に効く。
- 次の book でコマンド操作や Git、サーバー側のプログラムに進むときも、同じ公開先のまま続けられる。

第7章では、型3で公開先の選択肢と判断基準をAIに聞かせる。ただし**選ぶ体験までにとどめ、この本は Cloudflare Workers で進める**と明示する。読者ごとに公開先が違うと、第8章の切り分けを本が支えられなくなるためである。

## article との関係

編集方針2により、本文に画面の操作手順は書かない。しかし入口の読者には、どうしても具体が必要な場面がある。そこを article が引き受ける。

- 本文に書くのは「何を達成したいか」とプロンプトだけ
- どうしても具体が要る箇所から article へリンクする
- article は先頭に**確認日**を置き、末尾に「画面が違っていたらAIに聞いてください」と添える

この本から参照する article は、いまは「ファイルとフォルダの基本」（`/articles/files-and-folders`）の1本だけで、第1章と第4章から案内する。

エディタの導入（第4章）と Cloudflare Drop での公開（第7章）は、本文のプロンプトでAIに手順を聞かせる形で書いた。試読で読者が止まる場所が見えたら、その箇所だけを article に切り出す。画面が変わったときに article を1本差し替えれば済み、**本文は無傷で残る**。

## この本に書かないこと

サイト全体の編集方針（画面手順、コード全文）と、上の「やらないこと」に加えて、この本では次を書かない。

- 言語の文法の網羅的な解説（必要になった箇所で、必要なぶんだけ）
- 用語集（初出時の一言説明で足りる）
- 「おすすめの学習順」の提示（第10章と真正面から衝突する）

## 執筆と検証の順番

1. **第1章〜第4章と、ファイル・エディタの article** — 型と章の骨格が確定しないと以降が書けない。
2. **試読** — 1 が書けた時点で、実際に知識のない読者1〜2人に通しで進めてもらい、止まった場所とかかった時間を記録する。結果を骨格と目安時間に反映してから先へ進む。
3. **第5〜7章と、公開の article** — ここまでで「公開まで到達する一冊」として成立する。
4. **第8〜10章** — 到達の確認が揃い、この本の本題が完成する。

3 までで公開できる状態にはなるが、その時点では3つの目標がどれも到達の確認まで届いていない。**4 まで含めて1冊**である。
