# first-steps（仮題:AIと学ぶ、はじめてのソフトウェア開発）

この本の設計。章を書くときはここに従う。サイト全体の方針はリポジトリ直下の [README](../../../../../README.md) にある。

## 対象

ソフトウェア開発の知識がまったくない大学1年生をメインのペルソナとする。
高校生や、ソフトウェアの知識を仕事に活かしたい社会人も読めるが、書き方に迷ったらメインのペルソナで判断する。

サイトの入口にあたる一冊であり、**他のどの book / article も前提知識として要求しない**。ここだけは、本当に何も知らない読者から始める。

### 読者に用意してもらうもの

- パソコン1台とインターネット接続
- AIとの対話ツールをひとつ（どれを使うかは読者が選ぶ。特定のサービスに依存した書き方をしない）

それ以外は要求しない。アカウントや開発環境は、本の中で作る。

## この本のゴール

読み終えたとき、読者の手元に次の2つが残っている。

1. インターネットに公開された、自分のURL
2. この本がなくても学び続けられる、AIとのやり取りの型

1 は動機を保つための成果物であり、2 がこの本の本題である。

## 目標ごとの設計

サイト全体の3つの目標を、この本でどう扱うか。

### 目標1:次に何を学ぶかを、自分で決められる

**身につける力**

- ソフトウェア開発の全体像の中で、いま学んでいることがどこに位置するかを説明できる
- 作りたいものから逆算して、必要な知識と学ぶ順番を、理由をつけて決められる

**学習活動**

- 第1章で、ロードマップをAIからもらわせる。以降すべての章の冒頭で、その地図のどこにいるかを示す。
- 第11章で、次に学ぶことを**この本の外から**自分で選ばせる。選択肢はこの本が用意せず、選び方だけを渡す。

**到達の確認**

- 第11章。作りたいものを一つ決め、必要な知識の一覧と学ぶ順番を、理由つきで書き出せる

### 目標2:分からないことをAIに聞き、返ってきた答えの正しさを自分で確かめられる

**身につける力**

- 分からないことを、AIが答えやすい形の質問にできる(目的、前提、試したことを添える)
- AIの答えを、実際に動かした結果と、公式ドキュメントなどの一次情報の2つで確かめられる
- AIの答えが間違っていたり古かったりすることがある、と実感を持って理解している

**学習活動**

- 第2章で「聞く → 確かめる」の型を示し、以降の全章に「確かめる」節を必ず置く。

**到達の確認**

- 第10章。この本が扱っていない題材について、AIに質問し、得た答えを2つ以上の手段で確かめた過程を説明できる

### 目標3:詰まったときに、原因の場所を切り分けてAIに相談できる

**身につける力**

- 期待した動きと実際の動きの違いを、エラーメッセージから読み取った手がかりとあわせて説明できる
- 問題を再現し、範囲を狭めていく手順を踏める(一部を消す・戻す・分けて試す)
- 切り分けた結果をもとに、要点を絞った相談をAIにできる

**学習活動**

- 第4章で、読者自身が作った環境を**意図的に壊させて**、エラー相談の型を初めて使わせる。自分で壊したものは必ず直せるので、最初の練習として安全である。
- 第9章で、公開後に実際に起きた不具合に同じ型を使わせる。

**到達の確認**

- 第9章。初めて見る不具合について、原因がありそうな範囲を絞り込み、テンプレートに沿った相談文を書ける

### 各部の意図

- **第1部**は、手を動かす前に**迷子にならないための道具**を渡す。ここで渡した地図と型を、以降の全章で使い倒す。
- **第2部**は、読者の手元に「自分のもの」を作る。第4章で早めに壊しておくのは、第2部の残りで必ずエラーに出会うからである。
- **第3部**で成果物が外に出る。ここまでが、多くの入門教材が扱う範囲。
- **第4部**がこの本の本題。第9〜11章は**順に本の手を離していく**設計になっている。第9章は本の手順に沿って切り分け、第10章は本の指示なしで作り、第11章は本の外に出ていく。3つの到達の確認がここに集まる。

## 全編を貫く仕掛け

### 1. 学習ログ

序章で作り、全章が追記していく1つのファイル。編集方針1の「必ず成果物を残す」を章ごとにバラバラの物で満たすと散逸するため、**成果物の置き場所を最初に1つ決める**。

第9〜11章の到達の確認は、このログを読み返すことで判定できる。書き手は、各章の末尾に「学習ログに残すこと」を必ず置く。

第7章までは手元のテキストファイルで足り、第7章でリポジトリに移す。序章でGitHubアカウントを要求すると、そこで離脱する読者が出る。

### 2. 現在地の表示

各章の冒頭に、第1章で手に入れた地図を再掲し、いまどこにいるかを示す。目標1は読み物ではなく、**12回繰り返す習慣**で身につけさせる。

### 3. 型の反復

サイト全体で使う5つの型を、この本では次のように配置する。初出の章で型そのものを教え、以降は説明せずに使わせる。

| 型                   | 初出 | 繰り返し使う章 |
| -------------------- | ---- | -------------- |
| 型1・全体像を聞く    | 1章  | 5章、11章      |
| 型2・部分を聞く      | 2章  | 全章           |
| 型3・理由を聞く      | 2章  | 3章、6章、7章、8章 |
| エラー相談の型       | 4章  | 6章、8章、9章  |
| 公式資料を参照させる | 2章  | 3章、7章、8章、10章 |

## 章の書き方

全章を同じ骨格で書く。編集方針6の「反復」は、型だけでなく**章の形そのもの**にも効かせる。

```
ゴール（1文）
手に入るもの
目安時間
いま地図のどこにいるか

やること
    何を達成したいか → プロンプト（コピーしてそのまま送れる形）
確かめる
    実際に動かして確かめる
    一次情報で確かめる
つまずいたら（エラー相談の型へ）
学習ログに残すこと
次の章へ
```

「確かめる」を**構造として必須**にしておけば、編集方針4は書き手の心がけではなくテンプレートによって守られる。書き手が変わっても品質が落ちない。

これらの項目は `src/domains/book/book.ts` の `BookChapter` 型（`goal` / `deliverable` / `estimatedMinutes`）と対応しており、上の章構成の表からそのまま `meta.ts` を書き起こせる。

## この本に書かないこと

- 言語やフレームワークの文法の網羅的な解説（必要になった箇所で、必要なぶんだけ）
- 画面のスクリーンショットと操作手順（後述の article へ逃がす）
- 写経用のコード全文
- 用語集（初出時の一言説明で足りる）
- 「おすすめの学習順」の提示（第11章と真正面から衝突する）

## 技術の選択

第2部以降で作るものは、Cloudflare Workers に公開する前提で書く。

理由は、`https://developers.cloudflare.com/workers/llms.txt` のように**一次情報がAIに読ませられる形で整備されている**こと。「公式資料を参照させる型」を教えるうえで、これが決定的に効く。

ただし本文には、特定のサービスに読者を縛る書き方をしない。書くのは「何を達成したいか」であって、どのサービスを使うかは第8章で型3を使って読者自身に選ばせる。この本が示すのは選択の一例である。

## article との関係

編集方針2により、本文に画面の操作手順は書かない。しかし入口の読者には、どうしても具体が必要な場面がある。そこを article が引き受ける。

- 本文に書くのは「何を達成したいか」とプロンプトだけ
- どうしても具体が要る箇所から article へリンクする
- article は先頭に**確認日**を置き、末尾に「画面が違っていたら型1で聞いてください」と添える

想定される参照元は第3章・第7章・第8章。画面が変わったときに article を1本差し替えれば済み、**本文は無傷で残る**。

article は本文より先に書かない。第3章を書いてみて、どこで読者が詰まるかが見えてから書く。

## 執筆の順番

1. **序章〜第2章** — 型が確定しないと以降の全章が書けない。最優先。
2. **第3〜8章** — ここまでで「公開まで到達する一冊」として成立する。
3. **第9〜11章** — 到達の確認が揃い、この本の本題が完成する。
4. **article** — 2 と並行。

1 と 2 が終われば公開できる状態にはなるが、その時点では3つの目標がどれも確認まで届いていない。**4 まで含めて1冊**である。
