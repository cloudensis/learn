# first-steps（仮題:AIと学ぶ、はじめてのソフトウェア開発）

この本の設計。章を書くときはここに従う。サイト全体の方針はリポジトリ直下の [README](../../../../../README.md) にある。

## 対象

ソフトウェア開発の知識がまったくない大学1年生をメインのペルソナとする。
高校生や、ソフトウェアの知識を仕事に活かしたい社会人も読めるが、書き方に迷ったらメインのペルソナで判断する。

サイトの入口にあたる一冊であり、**他のどの book / article も前提知識として要求しない**。ここだけは、本当に何も知らない読者から始める。

### 読者に用意してもらうもの

- Windows または Mac のパソコン1台（ソフトを入れられるもの）とインターネット接続
- メールアドレスと、2段階認証に使えるスマートフォン
- AIとの対話ツールをひとつ（どれを使うかは読者が選ぶ。特定のサービスに依存した書き方をしない）

それ以外は要求しない。アカウントや開発環境は本の中で作り、**費用は0円、クレジットカードの登録も要らない**範囲に収める。

## この本のゴール

読み終えたとき、読者の手元に次の2つが残っている。

1. インターネットに公開された、自分のURL
2. この本がなくても学び続けられる、AIとのやり取りの型

1 は動機を保つための成果物であり、2 がこの本の本題である。
1 を第8章で手に入れたあとも動機が切れないよう、第4部は**そのURLのページを育てる形**で進める。

## 目標ごとの設計

サイト全体の3つの目標を、この本でどう扱うか。到達の確認は第4部に集まるが、途中の章の記録を**手応え**として位置づけ、第4部まで届かなかった読者にも「できるようになったこと」が残るようにする。

### 目標1:次に何を学ぶかを、自分で決められる

**身につける力**

- ソフトウェア開発の全体像の中で、いま学んでいることがどこに位置するかを説明できる
- 作りたいものから逆算して、必要な知識と学ぶ順番を、理由をつけて決められる

**学習活動**

- 第1章で、自分用のロードマップをAIからもらわせる。以降すべての章の冒頭で現在地を確かめさせる（→ 現在地の表示）。
- 第11章で、次に学ぶことを**この本の外から**自分で選ばせる。選択肢はこの本が用意せず、選び方だけを渡す。

**手応えと到達の確認**

- 手応え: 第1章のロードマップと現在地の印
- 到達: 第11章。作りたいものを一つ決め、必要な知識の一覧と学ぶ順番を、理由つきで書き出せる

### 目標2:分からないことをAIに聞き、返ってきた答えの正しさを自分で確かめられる

**身につける力**

- 分からないことを、AIが答えやすい形の質問にできる（目的、前提、試したことを添える）
- AIの答えを、実際に動かした結果と、公式ドキュメントなどの一次情報の2つで確かめられる
- AIの答えが間違っていたり古かったりすることがある、と実感を持って理解している

**学習活動**

- 第2章で「聞く → 確かめる」の型を示し、以降の全章に「確かめる」節を必ず置く。
- 第2章の題材は、一次情報で確かめられるもの（MDN などに説明があるもの）に誘導する。

**手応えと到達の確認**

- 手応え: 第2章の「答えを2手段で確かめた記録」
- 到達: 第10章。この本が扱っていない題材について、AIに質問し、得た答えを2つ以上の手段で確かめた過程を説明できる

### 目標3:詰まったときに、原因の場所を切り分けてAIに相談できる

**身につける力**

- 期待した動きと実際の動きの違いを、エラーメッセージから読み取った手がかりとあわせて説明できる
- 問題を再現し、範囲を狭めていく手順を踏める（一部を消す・戻す・分けて試す）
- 切り分けた結果をもとに、要点を絞った相談をAIにできる

**学習活動**

- 第4章で、読者自身が作った環境を**意図的に壊させて**、エラー相談の型を初めて使わせる。自分で壊したものは必ず直せるので、最初の練習として安全である。英語のエラーは訳さず、全文をそのまま渡させる。
- 第9章で、**本が用意した不具合**に同じ型を使わせる。第8章の最後に、手元では動くが公開先でだけ壊れる変更を加えさせておく。読者に原因は伝えない。不具合が起きるかどうかを偶然に任せない。

**手応えと到達の確認**

- 手応え: 第4章の「壊して直した記録」
- 到達: 第9章。初めて見る不具合について、原因がありそうな範囲を絞り込み、テンプレートに沿った相談文を書ける

### 各部の意図

- **第1部**は、手を動かす前に**迷子にならないための道具**を渡す。ただし序章で一度だけ、AIに頼んだページがブラウザに出る体験を先にさせる（インストール不要のHTML1枚）。道具の話だけが2時間続くと、そこで離脱する。
- **第2部**は、読者の手元に「自分のもの」を作る。第4章で早めに壊しておくのは、第2部の残りで必ずエラーに出会うからである。第3章は入門教材で最も離脱が多い環境構築にあたるため、article を最初に用意する章でもある。
- **第3部**で成果物が外に出る。ここまでが、多くの入門教材が扱う範囲。
- **第4部**がこの本の本題。第9章は本の手順に沿って切り分け、第10章は本の指示なしで作り、第11章は本の外に出ていく。**順に本の手を離していく**。題材はすべて第8章で公開した自分のページであり、新しい題材を持ち込まない。

## 全編を貫く仕掛け

### 1. 学習ログ

序章で作り、全章が追記していく1つのファイル。編集方針1の「必ず成果物を残す」を章ごとにバラバラの物で満たすと散逸するため、**成果物の置き場所を最初に1つ決める**。

- 各章の末尾に「学習ログに残すこと」を必ず置く。最後の1行は**次に再開する場所**にする。この本は何日かに分けて読まれる前提で、中断した読者が戻ってこられるようにする。
- 第9〜11章の到達の確認は、このログを読み返すことで判定できる。
- 第7章までは手元のテキストファイルで足り、第7章でリポジトリに移す。序章でGitHubアカウントを要求すると、そこで離脱する読者が出る。ログのリポジトリは**非公開**で作らせる。

### 2. 現在地の表示

ロードマップは2枚ある。

- **この本のロードマップ** — 本が持つ共通の1枚。各章の冒頭に再掲し、いまどこにいるかを示す。
- **読者のロードマップ** — 第1章で読者がAIからもらって作る1枚。読者ごとに中身が違う。

各章の冒頭では、本のロードマップで現在地を示したうえで、読者に「自分のロードマップではどこにあたるか」を照らし合わせさせる。ずれていれば、読者のロードマップを書き直させる。目標1は読み物ではなく、**12回繰り返す習慣**で身につけさせる。

### 3. 型の反復

サイト全体で使う5つの型を、この本では次のように配置する。初出の章で型そのものを教え、以降は説明せずに使わせる。1つの章で初出にする型は2つまでにする。

| 型                   | 初出 | 繰り返し使う章          |
| -------------------- | ---- | ----------------------- |
| 型1・全体像を聞く    | 1章  | 5章、11章               |
| 型2・部分を聞く      | 2章  | 全章                    |
| 公式資料を参照させる | 2章  | 3章、7章、8章、9章、10章 |
| 型3・理由を聞く      | 3章  | 6章、7章、8章、11章     |
| エラー相談の型       | 4章  | 6章、8章、9章           |

公式資料を参照させる型は、URLを開けないAIもあるため、**開けないときは本文を貼り付けて渡す**やり方もあわせて教える。

### 4. 詰まったときの共通ルール

序章で渡し、各章の「つまずいたら」から毎回ここへ戻す。

- **AIの答えが本文の例と違う** — 違っていて当然である。答えが一致するかではなく、章の「次へ進んでよい状態」になっているかで判断する。
- **同じところで3回止まった** — 最後に動いた状態に戻し、新しい会話で、ここまでの状況を要約してから聞き直す。AIと堂々巡りを続けない。
- **それでも解決しない** — 人に聞ける窓口へ案内する（窓口は公開までに用意する）。
- **AIにも、公開する場所にも載せないもの** — パスワード、APIキー、個人情報。序章で一度、第7〜8章で改めて扱う。

## 章の書き方

全章を同じ骨格で書く。編集方針6の「反復」は、型だけでなく**章の形そのもの**にも効かせる。

```
ゴール（1文）
手に入るもの
目安時間
いまロードマップのどこにいるか

やること
    何を達成したいか → プロンプト（コピーしてそのまま送れる形）
確かめる
    実際に動かして確かめる
    一次情報で確かめる
次へ進んでよい状態（ここまでできれば、残りは飛ばしてよい）
つまずいたら（共通ルールと、エラー相談の型へ）
学習ログに残すこと（最後は、次に再開する場所）
次の章へ
```

- 「確かめる」を**構造として必須**にしておけば、編集方針4は書き手の心がけではなくテンプレートによって守られる。
- 「次へ進んでよい状態」は、AIの特定の答えではなく**読者の手元の状態**で書く。AIの答えは読者ごとに違うため、答えを基準にすると判定できない。
- 読者に何かを選ばせる場面（第6章の機能、第10章の追加機能、第11章の作りたいもの）では、**例をいくつかと決め方を添える**。白紙で選ばせると、そこで止まる。

## 技術の選択

第2部以降で作るものは、Cloudflare Workers に公開する前提で書く。アカウント作成にクレジットカードが要らず、無料の範囲で最後まで進められる。

もう一つの理由は、`https://developers.cloudflare.com/workers/llms.txt` のように**一次情報がAIに読ませられる形で整備されている**こと。「公式資料を参照させる型」を教えるうえで、これが決定的に効く。

第8章では、型3で公開先の選択肢と判断基準をAIに聞かせる。ただし**選ぶ体験までにとどめ、この本は Cloudflare Workers で進める**と明示する。読者ごとに公開先が違うと、第9章の切り分けを本が支えられなくなるためである。

## article との関係

編集方針2により、本文に画面の操作手順は書かない。しかし入口の読者には、どうしても具体が必要な場面がある。そこを article が引き受ける。

- 本文に書くのは「何を達成したいか」とプロンプトだけ
- どうしても具体が要る箇所から article へリンクする
- article は先頭に**確認日**を置き、末尾に「画面が違っていたら型1で聞いてください」と添える

想定される参照元は第3章・第7章・第8章。画面が変わったときに article を1本差し替えれば済み、**本文は無傷で残る**。

## この本に書かないこと

サイト全体の編集方針（画面手順、コード全文）に加えて、この本では次を書かない。

- 言語やフレームワークの文法の網羅的な解説（必要になった箇所で、必要なぶんだけ）
- 用語集（初出時の一言説明で足りる）
- 「おすすめの学習順」の提示（第11章と真正面から衝突する）

## 執筆と検証の順番

1. **序章〜第3章と、第3章の article** — 型と章の骨格が確定しないと以降が書けない。第3章は離脱が最も多い章なので、article もここで書く。
2. **試読** — 1 が書けた時点で、実際に知識のない読者1〜2人に通しで進めてもらい、止まった場所とかかった時間を記録する。結果を骨格と目安時間に反映してから先へ進む。
3. **第4〜8章と、第7・8章の article** — ここまでで「公開まで到達する一冊」として成立する。
4. **第9〜11章** — 到達の確認が揃い、この本の本題が完成する。

3 までで公開できる状態にはなるが、その時点では3つの目標がどれも到達の確認まで届いていない。**4 まで含めて1冊**である。
